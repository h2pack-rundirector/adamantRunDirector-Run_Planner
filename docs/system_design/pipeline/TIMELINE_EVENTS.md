# Timeline Events

## Purpose

The fresh planner separates physical room traversal from encounter timing and
reward timing. A room is the container. Encounters and reward offers happen
inside or around that room at specific phases.

Runtime consumes compiled instructions derived from this history shape; see
`../runtime/RUNTIME_BOUNDARY.md`.

This avoids treating one room step as one encounter step. That approximation is
wrong for rooms such as O ships, where one physical room can contain multiple
encounters.

## Core Rule

```text
The current room generates the next rooms.
The entered next room is the result of the previous room's selected door.
```

In game terms, the planner is usually simulating the next room while the player
is still standing in the current room.

## Room Lifecycle

For a physical room node, the builder emits ordered events:

```text
room.enter
room.encounters
room.offer_points
room.generate_next
room.commit
```

### `room.enter`

The physical room becomes current. Room entry exists in history.

The room was already validated as a possible generated target when the previous
room generated its doors.

### `room.encounters`

The room's encounter sequence runs. A room may have zero, one, or many
encounters.

`RunEncounterDepth` and `BiomeEncounterDepth` advance from encounter events,
not from generic room entry.

### `room.offer_points`

Room-internal offer points are emitted here. Examples:

- shop offers inside a shop room;
- O wheel offers between ship encounters;
- any future room-local interaction offer points.

### `room.generate_next`

The current room generates all next-room doors and the offer points attached
to those doors.

Generated next-room eligibility and generated next-door reward eligibility are
checked at this phase. Reward offers inside all generated-door offer points
deplete reward bags at this phase, including unselected doors.

This happens before the current room commits to room history / biome depth
cache.

### `room.commit`

The current physical room is committed to room history.

`BiomeDepthCache` and room-history counters advance here according to the
room's declaration data and game behavior.

The selected generated door becomes the next physical room.

## Counter Views

History should expose typed views instead of one blended step counter:

- `RoomHistory`: committed physical rooms.
- `BiomeDepthCache`: biome-local room progression.
- `RunEncounterDepth`: route-wide counting encounter depth.
- `BiomeEncounterDepth`: biome-local counting encounter depth.
- `RewardOfferHistory`: all generated reward offers.
- `LootHistory`: acquired rewards only.
- `GeneratedDoorHistory`: generated next-room doors.

Validators must name the axis they query. "Depth" is not a sufficient concept.

## Room Eligibility Versus Encounter Timing

Room eligibility is checked when a room is generated as a door from the
previous room.

Encounter timing is simulated only after the room is entered.

Next-room eligibility is checked after the current room's encounter sequence,
when the current room generates its next doors.

## Reward Offer Timing

Door offer points are generated by the room that creates the door, not by the
room the door leads to.

For a normal generated door reward:

```text
current room generate_next phase:
  reward.offer
  reward bag depletion

selected next room entry/acquisition phase:
  reward.acquire if acquired = true
  loot history update
```

The canonical plan stores `acquired`; history expands that into offer and
acquire events at the correct phases.

## O Ship Example

An O combat ship with three encounters is one physical room with multiple
encounter events:

```text
room.enter O_Combat03
encounter.start intro       BED +0
encounter.start combat1     BED +1
offerPoint.emit wheel1
reward.offer wheel1
reward.acquire wheel1
encounter.start combat2     BED +1
offerPoint.emit wheel2
reward.offer wheel2
reward.acquire wheel2
room.generate_next
room.commit                 BDC +1
```

This is why room and encounter timelines must be separate. If the planner
increments `BiomeEncounterDepth` once on room entry by a precomputed total, it
collapses timing and can validate O story/shop conditions at the wrong point.

## Preboss Timing

Preboss is one structural room even when the game shows a shop path and a free
reward path. The free reward and shop offers are mutually exclusive reward
surfaces on the same generated preboss room, not two separate physical rooms.

## N Hub Timing

N is structurally different and should get its own traversal model, but one
timing fact is settled:

```text
room.enter N_Hub
  generate all pylon doors
  generate all pylon door rewards as a hub batch
```

Later room traversal and acquisition happen in the player's chosen pylon/side
room order.
