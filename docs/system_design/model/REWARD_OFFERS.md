# Reward Offers

## Purpose

Reward offers are concrete generated reward facts inside offer points. They are
separate from UI reward forms and from acquired loot history.

The planner needs this separation because reward bags deplete when rewards are
offered, while loot-history rules care about rewards the player acquired.

This is a focused companion to `REWARD_MODEL.md`, which owns the broader reward
system boundary.

## Canonical Shape

Rewards attach to offer points, not directly to rooms:

```lua
offerPoint = {
    kind = "generatedDoorRewards",
    batchKey = "nextDoors",
    offers = {
        {
            store = "RunProgress",
            rewardType = "WeaponUpgrade",
            acquired = true,
            payload = {},
        },
    },
}
```

A reward offer is concrete:

```lua
rewardOffer = {
    store = "RunProgress",
    rewardType = "WeaponUpgrade",
    acquired = true,
    payload = {},
}
```

Presence of a reward offer means the game generated or displayed it.

`acquired = true` means the player got it. `acquired = false` means it was
offered but not taken, bought, or entered.

## Offer Points

An offer point is the game moment that generates one or more reward offers.
The point owns timing and batch semantics; the individual offer owns store,
reward type, payload, and acquisition state.

Examples:

- generated next-door rewards;
- H cage rewards on a generated cage door;
- O wheel rewards after a ship encounter;
- N hub pylon rewards;
- shop offers inside a shop room;
- preboss shop/free-reward branch offers.

This keeps O honest: one physical room can contain multiple encounter-local
offer points without pretending the room itself has one reward surface.

## Offer Versus Acquisition

Reward history has two separate concepts:

```text
reward.offer
reward.acquire
```

All generated offers enter `RewardOfferHistory`.

Only acquired rewards enter `LootHistory`.

This supports the main bag rule:

```text
Reward bags deplete on offer, not acquisition.
```

An unselected generated door can deplete the bag even though it does not update
loot history.

## Generated Door Offer Points

Most route rewards are generated by next-room doors from the current room:

```lua
generatedDoors = {
    selectedDoorIndex = 1,
    doors = {
        {
            exitIndex = 1,
            targetRoomKey = "F_Combat07",
            offerPoint = {
                kind = "generatedDoorRewards",
                batchKey = "nextDoors",
                offers = {
                    {
                        store = "RunProgress",
                        rewardType = "MaxHealthDrop",
                        acquired = true,
                    },
                },
            },
        },
        {
            exitIndex = 2,
            targetRoomKey = "F_MiniBoss02",
            offerPoint = {
                kind = "generatedDoorRewards",
                batchKey = "nextDoors",
                offers = {
                    {
                        store = "RunProgress",
                        rewardType = "Boon",
                        acquired = false,
                    },
                },
            },
        },
    },
}
```

Both rewards are offered and can affect bag state. Only the selected/acquired
reward updates loot history.

## Structural Reward Offers

Some rewards are game-domain reward offers with structural consequences.
`ClockworkGoal` in I is the canonical example:

```lua
offerPoint = {
    kind = "clockworkGoal",
    rewardType = "ClockworkGoal",
    acquired = true,
}
```

It is still modeled as an offer point because the game models it as a reward.
The planner should not invent a separate goal-room key for it. The generated
door targets the real room, such as `I_Combat03`, and the offer point carries
`ClockworkGoal`.

Structural reward offers can drive biome counters, encounter selection, and
terminal-room eligibility. That means configured biomes must include reward
offer metadata; a structure-only configured biome is not a complete plan.

## Encounter Offer Points

O ship rewards are encounter-local offer points. They are sequential, not one
room-wide batch:

```lua
roomState = {
    kind = "ShipCombat",
    encounters = {
        { kind = "intro", encounterDepthCost = 0 },
        {
            kind = "combat",
            encounterDepthCost = 1,
            offerPoint = {
                kind = "shipWheel",
                offers = {
                    { store = "RunProgress", rewardType = "MaxHealthDrop", acquired = true },
                    { store = "RunProgress", rewardType = "RoomMoneyDrop", acquired = false },
                },
            },
        },
        {
            kind = "combat",
            encounterDepthCost = 1,
            offerPoint = {
                kind = "shipWheel",
                offers = {
                    { store = "MetaProgress", rewardType = "MemPointsCommon", acquired = true },
                },
            },
        },
    },
}
```

Wheel 1 can affect bag state before wheel 2 is generated.

## Reward Templates

Reward UI can be polymorphic and convenient:

- `MajorMinor`
- `Devotion`
- `RunProgress`
- `MetaProgress`
- `ShopOffer`
- H cage reward controls
- O wheel reward controls

These are authoring helpers. Completed canonical offers must resolve to
concrete facts:

- store key;
- reward type;
- acquired flag;
- payload when needed.

Completed canonical plans do not allow unresolved values such as Auto,
Vanilla, Major, Minor, or partial Devotion god choices.

## Batches

Some offer groups are generated together and should be modeled as batches for
bag refill/depletion rules:

- H cage offer points;
- N hub pylon offer points;
- normal generated next-door offer points from one room.

H cage offer points are derived from the Fields generated-door batch. The
batch owns the cage roll; target combat rooms own capacity; generated combat
doors receive the derived cage offer count.

O ship wheels are sequential offer points, not one room-wide batch.

Shop offers are shop-domain batches, but shops are not reward-bag
participants.

## Shops

Shops use shop domains/profiles, not reward bags.

Shop offers still matter to history:

- offered shop items can be pending store offers;
- bought items emit acquired loot;
- unbought items remain `acquired = false`;
- shop offers can participate in shop-domain validation.

Example:

```lua
{
    store = "WorldShop",
    rewardType = "HermesUpgrade",
    acquired = false,
}
```

## Preboss Rewards

Preboss is one structural room with a special reward surface.

For biomes with a free preboss reward option, the free reward and shop offers
are mutually exclusive reward branches on the same generated preboss room. They
are not separate physical rooms.

## Validator Usage

Validators should query the correct history:

- bag availability and refill: `RewardOfferHistory`;
- hammer counts, devotion spacing, and loot requirements: `LootHistory`;
- pending store/shop checks: active unexpired shop offers;
- batch duplicate/refill behavior: current reward batch plus prior offers.
