# Reward Legality And Bags Audit

## Purpose

This audit classifies the current planner reward rules before the fresh-start
model carries them forward.

It is supporting evidence for `REWARD_MODEL.md`, not the primary reward system
spec.

The main risk is treating reward-bag behavior as ordinary reward legality.
Those are different systems in the game:

```text
reward entry requirements decide whether a bag entry can be chosen
reward bags decide whether an entry is still present or whether the bag refills
loot history decides whether acquired rewards satisfy later requirements
```

The fresh model should keep those boundaries explicit.

## Classification Terms

`Bag Entry Requirement`
: A `GameStateRequirements` predicate attached to one counted reward-store
entry. It decides whether that specific entry can be selected from the bag.

`Bag Simulation`
: Counted store depletion, refill, and preservation. This answers whether a
specific reward can still be available after previous offers removed entries.

`Offer Batch Constraint`
: A same-generation restriction across offers in one batch, such as no
duplicate non-boon reward types in H cages.

`Shop Domain`
: A shop option set. Shops are generated offer domains, not reward bags.

`Loot History Rule`
: A rule over acquired loot/use records, such as "already had a Hammer."

`Meta / Unsupported`
: A save-state or game-state dependency the planner should not model unless it
becomes a user profile setting.

`Transitional Planner Approximation`
: A current planner rule that was useful before full reward bags, but should
not become fresh-start truth.

## Game Behavior Facts

`InitializeRewardStores` copies `RewardStoreData` into
`CurrentRun.RewardStores` at run start. These are counted bags, not unique
domains.

`ChooseRoomReward` iterates the current bag, filters entries through
`IsRoomRewardEligible`, chooses one eligible entry, removes that entry from the
bag, and stores the full selected reward data on the room.

If no entries are eligible, the game appends another full copy of the store and
tries again. It does not discard the ineligible entries already present.

`IsRoomRewardEligible` checks:

- same-batch duplicate blocking through `previouslyChosenRewards`, unless the
  reward entry has `AllowDuplicates`;
- room `EligibleRewards`;
- room `IneligibleRewards`;
- the reward entry's `GameStateRequirements`.

This means duplicate bag entries with the same `Name` can have different
eligibility. They are not interchangeable.

Reward offers are generated before acquisition. Door rewards are generated by
the current room while the player is still in that room. O wheel rewards are
generated during the current ship room's encounter sequence. N hub rewards are
generated as hub-door offers.

`RecordUse` updates `CurrentRun.UseRecord` and
`CurrentRun.BiomeUseRecord`. Loot pickup updates `CurrentRun.LootTypeHistory`
and `CurrentRun.LootBiomeRecord`. Fresh model queries should name the matching
game ledger instead of collapsing them into one generic reward history.

`RequiredNotInStore` checks the current room's shop options. In planner terms,
shop offers need a bounded `pendingOffer` interval. A pending shop offer should
block generated rewards only while the player is in that shop context.

Shop offer item names can differ from acquired loot-history names. For example:

- shop Hammer offer: `WeaponUpgradeDrop`
- acquired loot-history type: `WeaponUpgrade`
- shop Hermes offer: `ShopHermesUpgrade`
- acquired Hermes loot-history type: `HermesUpgrade`

The fresh model should represent offer type and acquired loot type explicitly,
or provide a declaration-owned normalization map.

## Current Bag Declaration Audit

`bags.lua` already moved in the right direction: bags are counted arrays and
unique `rewardStores` are derived mechanically for dropdown domains.

The missing part is per-entry requirement metadata. The game has multiple
entries with the same `Name` but different requirements:

- `RunProgress.MaxHealthDrop`, `MaxManaDrop`, and `RoomMoneyDrop` each have a
  plain entry and a later entry gated by prior god loot.
- `RunProgress.StackUpgrade` has two entries, both requiring
  `StackUpgradeLegal`, with one also gated by prior god loot.
- `RunProgress.WeaponUpgrade` has an early entry and a late entry with
  different Hammer requirements.
- `TartarusRewards.WeaponUpgrade` and `TyphonBossRewards.WeaponUpgrade` also
  have early and late Hammer entries.
- `HubRewards` contains five `Boon` entries and single conditional Hammer,
  Hermes, and Spell entries.
- `SubRoomRewards` and `SubRoomRewardsHard` contain counted entries with their
  own conditions, especially `StackUpgradeLegal` and `TalentLegal`.

Fresh bag declarations should therefore use counted entries, not only strings:

```lua
RunProgress = {
    { rewardType = "Boon" },
    { rewardType = "Boon" },
    {
        rewardType = "WeaponUpgrade",
        requirements = { named = "HammerLootRequirements" },
        acquiredLootType = "WeaponUpgrade",
    },
    {
        rewardType = "WeaponUpgrade",
        requirements = { named = "LateHammerLootRequirements" },
        acquiredLootType = "WeaponUpgrade",
    },
}
```

String shorthand is only safe for entries with no requirements and no
offer/acquire name split.

## Constraint Audit

`constraints.lua` contains offer-shape rules, not bag rules.

`devotionPair`
: Keep as Devotion payload integrity. The selected pair must be two distinct
boon sources.

`fieldsCages`
: Keep as an H batch/offer constraint. Game generation passes
`previouslyChosenRewards` across cage rewards, which prevents duplicate
non-duplicate reward entries in the same batch. This is not bag depletion.

`Q_WorldShop`
: Keep as a shop-domain same-group constraint. It belongs to shop profile
generation, not reward bags.

## Fresh Model Destination

The fresh reward pipeline should split into four validators/simulators:

1. `Offer Domain Validation`
   - Is the configured offer legal for this offer point's declared store,
     room filters, and shop profile?
   - Are all offer payloads complete?

2. `Entry Requirement Validation`
   - Does at least one matching counted bag entry exist whose game
     requirements are satisfied at the offer point?
   - Does the selected shop option satisfy its `ReplaceRequirements` or
     consumable requirements?

3. `Reward Bag Simulation`
   - Walk offer points in game timing order.
   - Remove every offered bag entry, including unselected generated doors.
   - Refill by appending a full store copy when no eligible entry exists.
   - Preserve ineligible entries already in the bag.

4. `Loot Acquisition History`
   - Only acquired offers update loot/use history.
   - Shop offers can be pending without being acquired.
   - Shop purchases should acquire the normalized loot type at the correct
     game phase.

## Queries The Fresh Model Needs

The query layer should expose game-language ledgers:

- `CurrentRun.LootTypeHistory[lootType]`
- `CurrentRun.UseRecord[name]`
- `CurrentRun.BiomeUseRecord[name]`
- `CurrentRun.LootBiomeRecord[lootType]`
- `CurrentRun.ClearedBiomes`
- `CurrentRun.EncounterDepth`
- `CurrentRun.BiomeEncounterDepth`
- `RequiredMinRoomsSinceEvent(event, count, axis)`
- `RequiredMinExits(count)`
- `RequiredNotInStore(name)`
- prior distinct god loot sources
- current offer batch duplicate set

Planner-only names such as `EnteredBiomes` should not be used when the game
uses a clearer ledger such as `ClearedBiomes`.

## Do Not Carry Forward

Do not carry these shapes into the fresh model:

- reward-type-global legality rules for conditions that are actually
  source-specific bag-entry requirements;
- broad alias groups such as `HAMMER_LOOT = { "WeaponUpgrade",
  "WeaponUpgradeDrop" }` as a substitute for offer/acquire normalization;
- one rule that says "Talent requires Spell" without also preserving the
  source-specific store entry requirements that differ by store;
- O-specific global exceptions for Devotion. O should differ because its room
  and offer source differ, not because Devotion owns a special exception;
- unique reward store domains as a replacement for counted bags.

## Open Implementation Questions

`StackUpgradeLegal`
: The game checks `CurrentRun.Hero.UpgradableTraitCount >= 1`. The fresh
planner needs a route-derived approximation based on acquired boon/trait
history, or a profile setting. Until then, classify it as an unsupported
entry requirement rather than pretending it is always legal.

`TalentLegal`
: The game includes `AllSpellInvestedCache`. This is save/run state outside
the current route plan. It should be ignored by default or exposed as a
profile input later.

`SpellDropRequirements`
: The game includes `PendingSpellDrop` and current-room chosen reward checks.
The fresh model can cover pending shop offers and current offer batches, but
should not model surface-shop pending spell state until surface shop purchases
are modeled.

Shop replacement logic
: Shop data often uses `ReplaceRequirements` rather than the reward bag
entry's requirements. Shop profile declarations should preserve these
requirements instead of relying only on reward primitive names.

Bag refill proof
: The simulator must answer "given the concrete offers so far, can this
configured offer be generated now?" That is stricter than current selected
legality and is the real point of the fresh reward-bag pass.
